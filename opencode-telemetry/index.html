What was actually measured

OpenCode stores every assistant step in a local SQLite database with three clocks: request start, end of streaming, and end of the whole step. That is enough to separate model speed from tool time — no stopwatch, no benchmark harness.

Method · how a step is timed

A step is one assistant message. created → streamed is the LLM request: prefill, queueing and generation. streamed → completed is tool execution plus the commit. Tokens are normalized: input is fresh input, cache reads/writes are separate, output excludes reasoning, and the recorded cost bills output + reasoning at the output rate. Counts in this panel cover the full history; the charts and tables below follow the filters.

Three numbers, often confused
Generated rate
(output + reasoning) tokens ÷ LLM seconds
Visible rate
output tokens only ÷ LLM seconds
Marginal decode
tokens ÷ added generation time, after fixed cost
Fixed overhead
prefill + TTFT + provider queue, paid every request

Reasoning is roughly half of all generated tokens here. Counting it is the only way to compare a thinking model with a non-thinking one; the visible rate is what you actually read. Every chart below responds to the filters above.

Reproduce it

The builder opens the OpenCode SQLite store read-only and never emits prompts, code or message text. Aggregates and compact per-step rows land in data/.

# from this directory
python3 telemetry.py

# or build, serve and open the report
python3 telemetry.py --serve

# optional filters
python3 telemetry.py --models deepseek --since 2026-09-01 --until 2026-10-22

# another store, omit titles, keep full paths
python3 telemetry.py --db ~/.local/share/opencode/opencode.db --no-titles --full-paths
The timing is reconstructed from the store, not from a live request. The query reads session_message rows where type = 'assistant'; time.created, time.streamed and time.completed are millisecond clocks. A step is timed only when 0.5s ≤ streamed − created ≤ 300s, it generated at least 20 tokens, and the implied rate is 3–400 tok/s.

Timing comes from OpenCode's own clocks: created → streamed includes prefill, provider queueing and generation; streamed → completed is tool execution plus commit. Output tokens exclude reasoning tokens — both are shown, and both are billed at the output rate in the recorded cost. Input is fresh input; cache reads/writes are separate. Recorded cost covers successful rows; totalSpendUsd adds error/empty ledger cost. Pricing varies by model, provider and era, so cross-model $/1M gen is not always like-for-like. The timed distribution is capped at 400 generated tok/s; valid fastRate/slowRate rows appear in the extremes, invalid timestamp artifacts appear in rejectedExtremes, and duplicate fork copies are counted separately. Negative fitted intercepts are constrained to zero and flagged. No prompts, assistant text, tool arguments or file contents are read or emitted. This is an observational analysis of one machine's history, not a controlled benchmark.
